# Display behavior

[中文](display-behavior.md) | English

> **Originality notice (important)**: This project is **an entirely original work**. It has no relationship with [JanEickholt/dsh-inline-diff](https://github.com/JanEickholt/dsh-inline-diff) or any other same-named/similar plugin or repository, and it is not a derivative or re-creation of any project; see the [README originality statement](../README.en.md) for details.

This document explains how inline diff cards and the “Expand / Whole file” dialog behave in terms of **data sources, refresh rules, line numbers, and dialog layering**, so you can tell what you are actually looking at. For version history see [CHANGELOG](../CHANGELOG.md); this document does not track version numbers.

## 1. Where card data comes from: an execution snapshot, not a live disk read

- When each `edit` / `write` execution completes, the tool result itself carries the **`before` / `after` file text** (`before` is empty for a new file).
- The plugin's Host side captures `{ path, before, after, operation }` when the tool result returns and stores it as an **in-memory** snapshot keyed by “session + call ID” (LRU, up to 240 entries; 4 MB per side, and writes exceeding the limit are not snapshotted). Nothing is written to disk and no network requests are made.
- When a card renders, it requests this snapshot from the Host once (the browser side also caches it by call ID to avoid duplicate requests); after that, **the card, the expanded dialog, and whole-file comparison all use this single copy of the data** and never read the file again.
- Therefore, clicking “Expand” or switching to “Whole file” only **shows the same snapshot in a different layout** — it does not re-read the disk, re-run the diff, or poll for refresh.

`str_replace_editor` and history replay do not have this Host snapshot: their cards switch to the `meta.diffs` change blocks carried in the tool result (already context-trimmed by the Host) and may read the current file once to fill in line numbers; this kind of display does not recompute whole-file alignment, so whole-file comparison is unavailable. The two are distinguished in their explanatory copy: `str_replace_editor` says “this tool call keeps no execution snapshot”, while only `edit` / `write` snapshots that have been lost (app restart, LRU eviction, exceeding the snapshot limit) are called “history replay”.

## 2. Refresh rules for whole-file comparison

- **The same card always shows the snapshot of that one edit**: `before` = the whole file before the call, `after` = the whole file after the call. Later edits do not retroactively change old cards.
- Closing the dialog and reopening the same card still shows **the same snapshot** (the browser caches by call ID; the Host also keeps the same copy by call ID); it never becomes the file's latest version.
- To view the file's latest content, open the card generated by **the most recent edit** and click “Whole file”; each card corresponds to an independent edit action.
- The plugin has no “old card observes the current file live” feature; this is intentional: a card represents a change event, not the file's current state.
- Calls that are still running and have not returned a result show only an **argument preview**: `edit`-type previews are based on the `old_string` / `new_string` fragments and show no exact line numbers; `write` previews are based on the written content with line numbers starting at 1. Once the result returns, the card switches to the execution snapshot.

## 3. History replay (fallback) and that one file read

- When the Host snapshot does not exist (DSH app restart, replaying an old session after the snapshot was evicted from the LRU, or a write exceeding the snapshot limit), the card degrades to **history-replay** mode:
  - only the changed hunks in the tool metadata and (best-effort) line numbers are shown, and the before-image cannot be restored;
  - the expanded dialog shows a **fixed notice banner** at the top, and the “Whole file” tab is greyed out;
  - in this case the card's first render additionally reads the **current file** once (read cache 15 seconds; requires the tool result to carry a file path), and uses it only to **fill in line numbers** — it never gains whole-file comparison that way.
- Line-number location is also based on the current file: if the file has changed since and the hunk cannot be located uniquely, the line numbers show “line numbers pending”, and the dialog explains the same. Deletion-only hunks may also fail to locate when the file offers too few context anchors.

## 4. The line-number gutter: OLD / NEW

- **In inline cards, every change with exact line numbers shows an OLD / NEW legend row strictly aligned with the gutter below its change header** (OLD in red, NEW in green); changes with pending line numbers show no legend. The expanded dialog instead uses the “Before / After” bars at the top to distinguish the two columns.
- The legend follows the line numbers that actually exist for the change: an ordinary change shows both OLD and NEW columns; a **new file** (new line numbers only) shows only NEW, and a **pure deletion** (old line numbers only) shows only OLD — no label is ever attached to a column that does not exist.
- Removed lines' old numbers are lightly tinted red and bolded; added lines' new numbers are tinted green and bolded; unchanged context lines keep gray numbers in both columns.
- Line numbers may be misaligned (e.g. old L454 corresponds to new L455); the change header gives the range “old Lx–Ly → new Lm–Ln”, and together with the legend you can quickly tell which column is before and which is after the edit.
- The content area of a collapsed inline card is at most 360px tall, and the diff area shows at most 42 lines in total (the line budget is allocated in change order); the remaining lines are described by a hint and can be viewed via “Expand” in the dialog.

## 5. Expanded dialog layering and scrolling

From top to bottom:

1. Title row: file icon, file name, language badge, operation and `+ / −` stats, old/new file line counts, “Changes / Whole file” switch, close button;
2. Notice banner (history replay, line numbers pending, whole-file comparison unavailable, etc., **appearing only when needed**);
3. “Before / After” bars;
4. Scroll area: change headers are sticky, with the comparison content below;
5. Bottom status bar (comparison source, old/new file line counts, `Esc · Close` hint).

The notice banner and the “Before / After” bars are **fixed headers** that do not scroll with the content; the scrollbar on the right belongs only to the scroll area, starts below them, and never covers the banner or title. Change headers stick at the top of the scroll area and only cover the comparison content, never the title, banner, or bars. Click the backdrop or press `Esc` to close the dialog.

The dialog is sized `min(1440px, 96vw) × min(900px, 90vh)`, is mounted to `document.body` through a React Portal, and layers above the host shell and third-party floating layers; on narrow screens (≤860px) the two columns stack vertically.

## 6. Settings dialog

- The dialog surface uses the theme's layered surface color (`#2c2c2e` deep gray in the official dark appearance, light in light appearance), keeping titles, descriptions, and controls at readable contrast; it never shows a washed-out gray panel from misusing the scrim color (`bg-overlay` is mid gray in the official dark theme).
- The title, description, and close button of “Inline Diff · Display” form a **fixed banner**, while the settings content scrolls independently below; the scrollbar never covers the banner and never scrolls it away.
- The dialog clips its own rounded corners, and both the scrolling content and the scrollbar stay inside the dialog — scrolling to the very top or bottom never overflows; the scrollbar keeps padding from the right edge and neither touches nor crosses the dialog border. On narrow screens (≤720px) each setting's controls stack vertically below its description.
- When “Other tool calls → Expanded” is enabled while “Process folding” is still DSH native, the plugin automatically switches it to “Unfolded” so completed tool rows are not hidden by DSH folding groups; “Reset to defaults” restores both the local options and the DSH transcript preference, and if “Other tool calls” changes as a result the page refreshes once automatically to apply it.
- The dialog and the settings page use the same panel; the bottom-of-sidebar “Diff style” opens the dialog, and “Inline Diff” in the DSH settings page embeds the same content.

## 7. IN / OUT on expanded-style cards

- Command and tool-call cards internally consist of **two segments, IN / OUT**, each with its own scroll area (IN capped at 180px, OUT capped at 260px); scrollbars hug the card's right edge (matching file-change cards), and text padding is kept by the scroll container itself so it is never pressed by the scrollbar.
- The left color bar shows status per segment, as a roughly 2.5px left stroke per segment: input preparing / awaiting output = theme color (pulsing), input side completed = green, input side failed = red; output running = theme color (pulsing, with a “Running…” placeholder), output succeeded = green, execution failed / non-zero exit = red, user aborted = warning color; when the input side fails, the OUT segment is marked “Skipped” and keeps a neutral color.
- Failure attribution: `INVALID_ARGS` / `UNKNOWN_TOOL` / `ABORTED_BEFORE_DISPATCH` go to the input side; all other execution-time errors, non-zero exit codes, and signal termination go to the output side; when the error code is missing, raw arguments that are not a valid JSON object also count as the input side. On input-side failures the IN code turns red, and on output-side failures the OUT code turns red; normal text uses the default foreground color that follows the inner tone and light/dark appearance. Failure text appears only in the corresponding IN / OUT segment, and the card ends at the IO panel without appending another repeated error line or an extra shell band below it.
- The status dot is green only when **both input and output succeed**; red when either side fails; warning color on user abort; theme color and pulsing while running/preparing.
- Only a single thin divider separates the two segments; the last segment's left stroke follows the card's bottom rounding, aligned with the card corners.

## 8. Large files and rendering performance

- Whole-file comparison renders at most 4000 lines; beyond that it truncates with a notice. When either side exceeds 4000 lines or the LCS alignment budget (4000 lines per side / 2.5 million cells) is exceeded, it automatically degrades to changed-hunk mode (with a notice banner in the dialog); if even the tool-metadata change blocks are missing, it uses prefix/suffix + replacement-block coarse alignment — colors and line numbers stay accurate, but move detection is turned off.
- **Materialization budget (new in 1.3.0)**: before splitting the text into per-line objects, the browser measures the budget first; when either side exceeds 200k lines or a single line exceeds 1,000,000 characters, per-line content is no longer materialized — only accurate line counts and added/removed totals are kept, and a “file too large” fallback notice is shown. This is the last line of defense against 4 MB-scale input producing millions of per-line objects that would freeze the page or exhaust memory.
- A collapsed inline card renders at most 42 lines (the line budget is shared across changes; a hint is shown for the rest); the card content area is at most 360px tall and scrolls internally.
- Syntax highlighting tokenizes the available data only once: when a whole side is within 200k characters / 4000 lines, it tokenizes the full text and indexes by line; otherwise highlighting is abandoned; history replay highlights locally per changed hunk. A single line over 2000 characters is not tokenized and falls back to the default foreground color.
- Inline token-level diff has its own budget: 4000 characters per line, 160k cells, and 2 million cells cumulatively per segment; when exceeded, that line shows whole-line coloring only.
- With many lines, fast scrolling through whole-file comparison can show a **brief flash / white flash**: this is the browser's rendering behavior when rasterizing a large syntax-highlighted DOM during scroll, combined with the dialog's background-blur compositing — a performance phenomenon. The data is a static snapshot and does not change because of the flicker; content and line numbers are always correct.
- Lazy rendering is not implemented yet; if it becomes necessary, it could render only rows near the viewport or reduce highlight density for very large files. The Read range observer only reacts to Read-row-related DOM changes and scans after the first frame, avoiding extra full-page queries during long sessions and startup animations.

## 9. Privacy

- By default no network requests, no telemetry; snapshots are kept only briefly in Host memory and never persisted; settings are written only to the browser's `localStorage` and contain no file contents.
- Exception: when the user explicitly clicks “Check for updates / Install”, the Host fetches npm registry metadata and invokes the local `dsh` CLI to install the plugin. Those requests contain only the package name/version — never session content, file content, keys or device information — and nothing runs in the background automatically.

## 10. Motion

Motion only serves “appearing” moments; there are no decorative loops:

- **Running card entrance**: when a command/tool card mounts while still “preparing / running”, it plays a one-shot 200ms fade-in with a 4px rise; historical replay, settled cards, and calls that finish in milliseconds render their final state immediately with no animation.
- **Output arrival**: when OUT switches from the “Running…” placeholder to real output, the OUT segment plays a one-shot 160ms fade-in with a 2px rise; re-renders that do not change status never replay it.
- **Dialog open**: the settings and side-by-side dialogs fade the overlay in over 140ms and fade/scale/dialog-rise over 200ms.
- **Performance and accessibility**: only opacity/transform are animated (no layout reflow); the easing is a strongly damped ease-out curve with no bounce, overshoot or exaggerated travel; everything is disabled under `prefers-reduced-motion: reduce`.
- Animations affect only this plugin's own DOM, never DSH native rows, third-party themes or startup-animation plugins.

## 11. Version & updates panel

- The “Version & updates” section at the bottom of the settings panel shows the current version, current DSH version, a “Check for updates” button, every npm version (Latest / Installed / Deprecated / Unavailable, publish date) and an “Update to / Roll back to / Reinstall” button.
- “Check for updates” is proxied by the Host to npm registry (60s cache, 12s timeout); external network is touched only on user action, and the payload contains only the package name and version numbers.
- “Install” is available on Web profiles only: the Host reuses the existing same-origin/loopback admission, validates that the target version exists in the registry list and is installable, then serially invokes the official CLI (`dsh plugin --profile <name> add @him666233/dsh-inline-diff@<version>`; argv only, no shell, 240s timeout kills the process tree), and verifies the installed version in `node_modules` afterwards.
- After installation you **must restart DSH** (restart `dsh web` for Web, restart the app for Desktop) to load the new version; a page refresh is not enough.
- Desktop v1 follows the official “fully quit the desktop app before changing a desktop profile” rule, so it shows the version list plus a copyable command instead of an in-place one-click install.
- Failure paths: nonexistent/unavailable/invalid versions are rejected before installing; when the CLI fails, the official installer rolls the profile back automatically and the panel shows the error code and log tail; only one install job may run at a time.
